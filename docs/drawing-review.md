# What the automated pass found in `25_114D_NOC_WAT_13.0_RevF.dwg`

Generated by `tools/gv_extract.py` and compared against the **GATE VALVE
COORDINATES** table already in the drawing (the copy carried in
`GV_POINT.dwg`). Of 173 table rows, **167 agree with the block positions to
within 20 mm**. The rest are listed here.

All coordinates are the survey grid the drawing is modelled on
(E ≈ 477 000–479 100, N ≈ 2 743 700–2 745 100).

## 1. `GV5` is missing from the table — two rows are both labelled `GV6`

The table has no `GV5`. Two consecutive rows are labelled `GV6`:

| Row | Label in table | Easting | Northing | Actually |
|---|---|---|---|---|
| 5 | `GV6` | 477853.859 | 2744393.148 | this is **GV5** |
| 6 | `GV6` | 477696.890 | 2744282.527 | this is GV6 |

The drawing itself is right — there is a `GV5` label in model space at the
first position. Only the table row is mislabelled. Every comparison below
treats that first row as `GV5`.

## 2. One gate valve has no `GV` label and is not in the table

There are **174** gate-valve blocks in model space but only **173** `GV<n>`
labels. The unlabelled one is at:

| Easting | Northing |
|---|---|
| 477149.577 | 2744103.507 |

`gv_extract.py` and `GVLIST` both continue the sequence and call it `GV174`,
flagged `auto-numbered (no GV label in drawing)`. It needs either a label and a
table row, or confirmation that it is not a scheduled point.

a later nudge of the symbol, rather than with a transcription error.

## 4. `GV139` and `GV173` sit close enough to confuse a naive match

Their labels are ~7 m apart, close enough that matching each valve to its
*nearest* label assigns them to each other's symbol. The table is correct; a
distance-only tool is not. This is why both tools run the second matching pass
described in the README — with it, GV139 and GV173 come out agreeing with the
table to 2 mm.

Worth knowing if this list is ever rebuilt with a different script.

## Note on `GV_POINT.dwg`

`GV_POINT.dwg` holds the GV1 valve, its label and a copy of the coordinate
table, pasted into a local coordinate system rather than the survey grid. The
relationship is a pure translation, no rotation or scale:

```
Easting  = X + 508213.73975
Northing = Y + 2741920.16532
```

Check: GV1's block sits at WCS `(-30171.614, 2372.170)` → `(478042.126,
2744292.335)`, against `(478042.125, 2744292.332)` in the table.

Its `X1` / `Y1` callout attributes still read `E=-30171.440` / `N=2372.138` —
raw WCS values that were never converted — while `Y2` was hand-edited to the
correct `N=2744292.332`. Running `GVSETUP` with the offsets above, then
`GVLABEL`, produces the converted values directly.
